# ADR 0007: Conformance runs the real workflow; reports are signed, local, and make a narrow claim

Status: proposed (RC1-641)

## Decision

**Conformance runs ESP's own workflow inside the installed machine.** `kit.verify run` ships one standard-library script (`kit/verify/machine.py`) into the running app over `fly ssh` and runs it with the image's Python, so every step uses the installed release's code and the machine's own secrets and network. The script drives ESP's CLIs: `conformance fixture`, then `executor.run` on the draft spec (it must be refused), `mapping.review approve`, the executor on a spec that was changed after approval (it must be refused), then `executor.run --execute --verify-convergence`, `executor.reconcile`, and `conformance cleanup`. ESP v0.1.4 (ADR-0029 in that repo) first made this possible: until then the image held only the review gate.

**The approval is the gate's, not the web app's.** The approval goes through `mapping.gate.approve` (the CLI), not `/api/approve`. The app serves one fixed spec, and approving through it would change the customer's live gate state. Identity is checked separately, over the app's public API in the profile's password mode: an anonymous write gets 401, a wrong password gets 401, the configured password signs in (`/api/me`), and the sign-in shows up in the audit log, which proves the app role can still INSERT into `review_audit`.

**Namespaced per run.** Each run uses a fresh fixture: addresses `cik-<run>-NNNN@example.com`, and an audience, list and campaign named `cik-conformance <run>`. A rerun therefore can never pass by converging onto an earlier run's records. The run directory in the machine is deleted afterwards.

**Cleanup is the one exception to "destination writes are never reversed" (ADR 0006).** It deletes only the run's own fixture contacts, list and campaign. ESP's cleanup refuses any name or address outside the run's namespace before it reads a credential, and it keeps a list that holds a contact the run did not create. What remains is reported (CNF-040). The sign-in probe's two audit rows (`sign_in`, `sign_out`) stay, because the log is append-only by design. The report states both side effects.

**Outcomes: pass, fail, insufficient_evidence.** Checks CNF-001..040 (`kit/verify/checks.py`) are pure functions over the collected evidence.
- A check whose prerequisite did not pass is `insufficient_evidence`, never `pass`.
- Malformed evidence is `insufficient_evidence`, never a crash.
- A refused write or an unreachable dependency can therefore only fail a run or leave it short.
- Destination state is judged two ways: ESP's reconciliation, and an independent read of the run's contacts by the cleanup process before it deletes them. Those must equal the fixture's exported total.
- Suppression integrity must be 100% over a fixture that actually contains suppressed records. With none, the check is vacuous and reported as `insufficient_evidence`.
- `/healthz` is recorded as CNF-002 and is never sufficient on its own.

**Why CNF checks are not in `checks.toml`.** ADR 0005's registry describes single-probe observations with a four-outcome vocabulary. Conformance checks judge multi-step workflow evidence with the three outcomes this phase requires. They use their own `CNF` area of the same `<AREA>-<NNN>` ID space, are never reused, and are versioned by `check_version` in the report. Triage can cite them by ID.

**The report, `cik.conformance/1`.** It holds:
- the run ID and install ID,
- the release (version, digest reference, commit),
- `check_version`,
- start and finish timestamps,
- the verdict and per-outcome summary,
- every observation with its reason and evidence,
- evidence references (name, sha256, bytes) to files under `conformance/<run>/evidence/`,
- the side effects,
- the integrity non-claim.

Every evidence file and the payload are scanned for the workspace's secret values. A hit discards the run's output.

**Integrity: the install's key signs the exact bytes.** The envelope `cik.signed/1` carries the canonical-JSON payload as a string, its Ed25519 signature, and the key fingerprint. The key is ADR 0003's per-install keypair, generated by `kit.install`, with the private half mode 600 on the customer workstation. `kit.verify verify-report REPORT --record install-record.json` refuses:
- a record whose public key does not match its own fingerprint,
- a report signed by any other key,
- any change to the payload,
- a report naming another install.

**Trust distribution.** The vendor learns the public key from the install record the customer shares (trust on first use). The customer reads the fingerprint to the vendor over a second channel (call or ticket) at first contact. A re-keyed install shows a different fingerprint and is refused until that confirmation is repeated.

**The claim, stated in every report and by `verify-report`.** A valid signature shows the report is unmodified and was signed with this install's key. It does **not** show the observations are true: the customer controls the environment and the key (ADR 0003's non-claim).

**Reports stay local.** `run` writes into the install workspace and nothing more. `export RUN_ID --out DIR` copies only the signed report, plus evidence with `--with-evidence` (the journal names the destination account). `kit.verify` contains no network client for reports; a test pins that.

- **Install:** `kit.install install` of ESP v0.1.4 (digest `sha256:957bc24a…`) created app `cik-esp-p3` against a throwaway Neon branch (`rc1-641-conformance`) of the customer project.
- **Destination key:** the customer's own Brevo key went into the workspace secrets file only, never into a vendor repo.
- **Preflight state:** the install ended `installed`, not `installed_not_ready`. ENV-001 passes for the first time because the app now holds a destination key.

**Findings the exercise forced:**
- **Brevo reactivation is not instant.** For about 4 minutes after the key was re-enabled, roughly 25% of calls (any endpoint, any page size) still returned 401 `API Key is not enabled`. 20 of 20 calls succeeded by 23:56. ESP correctly treats 401 as fatal and does not retry it. Consequence for the fault matrix (Phase 6): a family-2 restore must wait for propagation (probe until clean) before it is measured. Otherwise the "restored" case fails for a reason that is not the fault.
- **Scale-to-zero vs `fly ssh`.** The machine suspended itself while idle, and SSH then failed silently (empty output). Conformance is not exposed to this, because its health and identity requests go through Fly's proxy and wake the machine first. The runner now says so where the order is set.

Report integrity, on run 1's report:
- `verify-report` against the install record: valid, with the non-claim printed.
- The same file with its verdict edited to `fail`: refused, exit 4 ("modified after signing").
- The genuine file against a record carrying another key: refused, exit 4, naming both fingerprints.
- `export`: copied `report.signed.json` only.

## Consequences

- Each run leaves two audit rows in the customer's log, by design.
- Conformance needs a destination key in the app (`ESP_BREVO_API_KEY`). Without one the executor is refused and the run fails CNF-030; it never passes.
- The fixture runs against the customer's real destination account, inside its own namespace. A customer who wants it elsewhere points the app at a sandbox account; the kit does not provide one.
